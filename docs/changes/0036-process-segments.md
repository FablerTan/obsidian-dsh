# 0036 过程行按正文分界拆分

## 1. 背景与问题

**现象**：一轮对话里 AI 在「思考 / 工具调用 → 正文 → 思考 / 工具调用」之间来回切换时，原生面板只显示**一条**过程行；正文虽然单独成段，但全部排在过程行之后，展开后思考 / 工具的顺序也与正文对不上。

**用户截图**（vault 里「帮我给这个项目进行git初始化」这一轮）：

- 正文 1「I'll start by inspecting…」→ 一条过程行「运行了代码，执行了命令，写入了文件 · 用时 75 秒」→ 正文 2 / 3 / 4；
- 期望：以正文为分界线，正文前的过程、两段正文之间的过程各成一条过程行；
- 现状：所有思考 / 工具都进了第一条，正文被挤到后面。

**实测数据**（本机 3088 会话「移除项目 Git 初始化」，CDP 读原生面板 React fiber 拿到的快照）：

- turn 1 共 14 个 `assistant-step`、13 个 `tool-call` 节点，正文出现在 step 1 / 5 / 10 / 14；
- 原生面板 DOM 里 turn 1 只有 **1 个** `.dsh-native-process` 项，它的 head 显示「运行了代码，执行了命令，写入了文件 · 用时 75 秒」，后面紧跟 3 段正文；
- 也就是说数据侧顺序完整（step 与正文按块顺序交错），是**渲染模型**把顺序拍平了。

**根因**（[timeline-model.ts](../../src/view/native/ui/timeline-model.ts)）：

- `buildTimeline` 以 **turn** 为键建过程组（`groupFor`，约 163–183 行），同一轮所有 `reasoning` / `tool-call` 块与 `tool-call` 节点都往**这个已存在的组**里追加（194–240、271–276 行）；
- 正文 `flushText` 只是把 `TextItem` 追加到 items（198–218 行），**不会关闭当前组**；之后的过程成员继续进旧组，而旧组在 items 里的位置早于正文 → 正文之后发生的过程全部被渲染到正文之前；
- 组为空时正文会插到组前面（211–217 行，0016 的「先说话再动手」）；这只能处理「正文 → 工具」，处理不了「工具 / 思考 → 正文 → 工具」。

**影响**：长回合（本例 75 秒、13 次工具）折叠成一行后信息密度极低；展开层里思考 / 工具与正文顺序错位，误导阅读；与用户对「过程应该分段」的直觉冲突。

**相关历史**：[0016](0016-process-fold-rendering.md)（按 turn 折叠的初版，其「风险」表已提到「少见的 text / tool 交错步骤顺序不完美」）、[0017](0017-native-streaming.md)（live 合成 assistant-step）、[0035](0035-agent-team-support.md)（团队工具行）。

## 2. 目标与非目标

- 目标：
  - 以正文为分界线，把一轮里的过程拆成多段，**每段一条过程行**，顺序与真实发生顺序一致；
  - 没有正文分隔的连续步骤仍然合成一段（保持现有信息密度，不变成「一步一行」）；
  - 运行中 / 停止 / 出错状态、用时、展开折叠、工具行与思考行内部渲染不回退；
  - live 流式期间分段稳定：正文只出一半时不重复、不抖动，收尾后正式节点接管无跳变；
  - 历史会话（含 hidden 的 `tool-call` 节点）同样正确分段。
- 非目标：不改桥协议 / 桥版本、不改 dsh 侧插件、不做官方「轨迹」视图、不改正文 Markdown 排版与工具行样式、不做虚拟滚动。

## 3. 实现路径调研（≥ 2 条，先问用户选哪条）

| 路径 | 做法 / 关键代码位置 | 改动面 | 代价与风险 | 结论 |
|---|---|---|---|---|
| **A（推荐）** | 在 [timeline-model.ts](../../src/view/native/ui/timeline-model.ts) 内把「每轮一组」改成「每轮每段一组」：正文 flush 时关闭当前段；本轮维护 `openGroup` + 段序号；过程成员到来时若没有 open 组就新建（key 形如 `process:turn:<turn>:<seg>`）。另加 turn 内 `callId → 所在段` 映射，保证后到的 `tool-call` 结果节点并回工具块所在段而不是当前段；`turn-tail` 关闭该轮所有仍 open 的段（通常只剩最后一段）。live 走同一套块顺序逻辑，段序号由正文 flush 次数自然产生，key 稳定 | 单文件约 100–150 行；`timeline-process.tsx` 未改（口径 a 不需要） | 中等；无协议 / 数据 / 服务重启。风险集中在分段边界、空占位组清理、跨段工具结果合并、live↔settle 切换；用合成快照冒烟 + CDP 真实会话回归可覆盖 | **推荐**：数据侧已完整，分段是纯派生逻辑，改动集中在一个纯函数模型 |
| B | 桥侧算分段：`packages/dsh-obsidian-bridge/lib/client.js` 投影时给 block / node 加 `segment`（或把 assistant-step 拆成段节点），UI 按 `turn + segment` 分组 | 桥（client.js）+ [native-types.ts](../../src/shared/native-types.ts) + timeline-model；桥版本升 v7、桥文档、重启服务 | 高；收益低——块顺序已在 `assistant-step.data.blocks` 里，segment 只是派生值；扩大桥契约会牵连所有消费方与版本兼容 | 不推荐 |
| C | 只按 `assistant-step` 切分（每步一条过程行）：组 key 改成 `turn + step`，约 20–30 行 | timeline-model.ts 小改 | 低，但**修不彻底**：实测 step 1 = [正文, 工具]、step 5 / 10 = [思考, 正文, 工具]，同一 step 内正文之后的过程仍会进同一条行，截图场景依旧错位 | 不推荐 |
| D | 仍只有一条过程行，把正文作为条目按块顺序插进折叠体（展开后正文与过程交错） | timeline-model + timeline-process + 正文渲染 | 中；正文会失去独立消息排版 / 引用链接 / 流式纯文本快通道，且不符合「应该有多条栏」的预期 | 不推荐 |

> **推荐 A 的理由**：分段所需信息（block 顺序、turn / step、callId、closing 状态、timing）在现有快照里都有；不碰桥、不重启服务，风险与改动面最小；C 已被实测数据证伪，B 属于把纯派生逻辑搬到桥里、徒增协议面。

## 5. 行为变化

以截图那一轮为例（实测数据）：

- 现在：正文 1 → 过程行（13 次工具合并，75 秒）→ 正文 2 / 3 / 4；
- 改后：正文 1 → 过程行 A（step 1 的工具）→ 正文 2 → 过程行 B（step 2–5 的思考 / 工具）→ 正文 3 → 过程行 C（step 6–14 的思考 / 工具）→ 正文 4；每行 head 只统计**自己段内**的工具类别（「写入了文件」不再被算进只含 step 1 工具的第一行）；
- turn 2：正文 1 → 过程行 A（工具 1）→ 正文 2 → 过程行 B（工具 2）→ 正文 3；
- 没有正文分隔的连续步骤仍然只有一行；只有正文的回合仍然只有正文、不出现过程行；
- 运行中：当前段显示「思考中 / 运行代码…」+ 脉冲；之前已结束的段显示收尾摘要，不再脉冲；
- 停止 / 出错：之前已由正文结束的段保持「已完成」，只有最后一段显示「已停止 / 执行出错」；
- 用时：口径见 §8（默认推荐每段各自算，边界 step 的时间会同时算进前后两段）。

## 6. 风险与回滚

| 风险 | 影响 | 回滚方式 |
|---|---|---|
| 分段边界与实时流式不同步 | live 期间多出 / 抖动过程行，收尾后跳变 | 合成 live 快照用例覆盖「正文 → 思考 → 工具」逐步长出的过程；CDP 实时回合回归 |
| 后到的 `tool-call` 结果节点落错段 | 工具行重复或结果丢失 | turn 内 `callId → 段` 映射；加「结果节点在正文之后到达」用例 |
| 空占位组（`turn-process` 建立的「思考中」）不清理 | 正文前后各出现一条空过程行 | 正文 flush 时删除空组；过滤规则补用例 |
| 旧会话 / 停止 / 出错状态判定回退 | 停止回合被误标「已完成」 | 沿用现有 `processStatusOf` / `closing` 判定，只把状态从“整轮”改成“最后一段”，加合成用例 |
| 用时在段间重复计算 | 相邻两段用时之和大于本轮总时长 | §8 选择口径；必要时只保留最后一段用时 |

纯 UI / 纯函数改动，无数据迁移；回滚只需还原 `timeline-model.ts`。

## 7. 验证

**自动化**

- `npm run build`、`npm run check` 通过；
- 纯函数冒烟（esbuild 到 /tmp，直接调 `buildTimeline`，与本次调研用的复现脚本同路径）：
  1. 一轮内 `正文 → 工具 → 正文 → 思考 → 工具` → items = text, process, text, process，且两个 process 的 entries 不串；
  2. 连续多个 step 无正文 → 仍只有一条过程行；
  3. live blocks 逐帧增长（text → text+reasoning → text+reasoning+tool）→ 段序号 / key 稳定、正文不重复；
  4. `tool-call` 结果节点在正文之后到达 → 并回原段，不产生重复工具行；
  5. 只有正文的回合 → 0 条过程行；
  6. stopped / error 回合 → 前面的段 settled、最后一段 aborted / error；
  7. 空占位组在正文 flush 后被移除。

**CDP 手动回归**（本机 3088 + Obsidian 1.14.5，隐藏 core 打开同一会话）

- 打开「移除项目 Git 初始化」会话，读取 `.dsh-native-timeline` 直接子元素顺序；
  **验收标准**：turn 1 = 正文 → process → 正文 → process → 正文 → process → 正文（3 条过程行、4 段正文），turn 2 = 正文 → process → 正文 → process → 正文（2 条过程行、3 段正文）；
- 每条过程行 head 的类别只包含本段工具（第一行不再出现「写入了文件」）；
- 展开任意过程行，思考 / 工具顺序与该段 `assistant-step.data.blocks` 顺序一致；
- 实时发一条多轮工具消息：段随正文增长逐条出现，收尾后不跳变；
- 停止按钮中断一轮：最后一段显示「已停止」，之前的段保持「已完成」。
