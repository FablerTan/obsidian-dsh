# 0018 边用边改：需求登记 + 路径先选的工作流

## 1. 背景与问题

- 插件（0.4.1）已经可以日常使用，用户接下来会**边用边提需求**，而不是继续按 M3 → M5 的预设里程碑推进。
- 旧路线图把「数据互通（M3）」「CI / 发布（M5）」写成下一步，与真实使用节奏脱节，也看不出用户提了哪些需求、做到哪了。
- 旧提案流程只有一个方案：agent 直接写一个自认为最好的方案让用户批准，**用户没有选实现路径的机会**；需求与提案之间也没有统一账本，容易漏。

## 2. 目标与非目标

- 目标：
  1. 路线图顶部新增「主线：边用边改」+「需求待办」表，用户每提一个需求登记一行 `R-<n>`，并链接到 `docs/changes/` 提案。
  2. 把「需求 → 登记 → 调研 ≥ 2 条实现路径 → 用户选路 → 批准 → 执行 → 收尾」固化成硬规则（AGENTS.md 规则 12、13），并在 development / changes 索引 / project-guide 技能里给出同样口径。
  3. 未完成的 M3 / M5 余项转入「候选池」，不再按里程碑排期。
- 非目标：
  - 不改任何运行代码、构建产物、版本号；
  - 不重排 / 删除已完成的 M0–M7 历史；
  - 不新建 `docs/proposals/` 之类的新目录（先复用 `docs/changes/`）。

## 3. 实现路径调研

| 路径 | 做法 | 改动面 | 代价 / 风险 | 结论 |
|---|---|---|---|---|
| **A（采用）** | roadmap 内置「需求待办」表；提案内新增「实现路径调研」小节（≥ 2 条 + 推荐） | `docs/roadmap.md`、`docs/changes/README.md`、`AGENTS.md`、`docs/development.md`、技能 | 文件少、单处可查；长调研会让提案变长 | **推荐**：与现有「提案先行」衔接最自然 |
| B | 每个需求额外建 `docs/changes/NNNN-<slug>-paths.md` 独立调研文档，roadmap 引用两份 | 同上 + 每需求多一个文件 | 路径文档更独立，但文件翻倍、两份要同步、冷启动要读更多 | 需求跨仓库 / 调研超过一屏时再升级，本次不采用 |
| C | 只改 AGENTS.md 文字，不建 roadmap 待办表 | `AGENTS.md` | 改动最小，但没有可追踪账本，用户看不到待办全貌 | 不满足「roadmap 简短列待办 + 引用提案」的要求 |

> 以后遇到复杂需求，允许在 A 的基础上把长调研放到独立文件，并在提案的「实现路径调研」里链接过去；入口始终是提案。

## 5. 行为变化

- **运行时行为：无**（纯文档与流程）。
- 对用户：每个新需求都会先在 roadmap 出现一行待办，并有一份带路径对比的提案；agent 写完路径会停下来问选哪条，不再直接开工。
- 对 agent：需求到达后不再「边想边写代码」，必须先落 roadmap 行 + 提案，再等用户选路。

## 6. 风险与回滚

| 风险 | 影响 | 回滚方式 |
|---|---|---|
| 小需求也走全套流程，变重 | 交互变慢 | 保留既有例外：只改文档 / 注释 / 格式、用户当轮已明确指定项、单纯重建产物 |
| roadmap 待办与提案状态不同步 | 账本失真 | 规则 13 要求两边互链、状态一致；收尾时同时改 `done` 与 `✅ 已完成` |
| 路径调研写成「凑数对比」 | 用户仍无从选择 | 提案模板要求每条路径写改动面 / 代价 / 风险，并标明推荐与不推荐理由 |
| 文档链接 / 锚点失效 | 冷启动走错 | 本次改完逐条检查相对链接；`npm run check` 兜底构建一致性 |

回滚：纯文档改动，`git checkout` 对应文件即可，不涉及产物与版本。
