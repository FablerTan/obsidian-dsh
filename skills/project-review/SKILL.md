# 项目审阅（obsidian-dsh）

一句话：**只读体检 → 分级报告 → 用户拍板 → 按提案分批重构 → 验证收尾**。审阅阶段**不改任何代码**；重构阶段**不改任何功能**。

三层分工：本技能 = 审阅与重构流程；`skills/project-guide/SKILL.md` = 落位决策、拆分判据与验收清单；`AGENTS.md` = 硬规则（冲突以它为准）；`docs/changes/` = 提案账本。

> 本技能与 `project-guide` 一样，通过 `.dsh/skills/` 下的符号链接被访问（接入方式见 `docs/skills.md`），
> 因此文中一律用**仓库相对路径**（如 `docs/roadmap.md`），不用 `../` 相对链接。

本技能的文件：

| 文件 | 作用 |
|---|---|
| `skills/project-review/SKILL.md` | 本文件：流程、边界、批次纪律、验收清单 |
| `skills/project-review/scripts/audit.mjs` | 只读扫描器：机械产出候选 findings（命令与契约见第 2.2 节） |
| `skills/project-review/references/checks.md` | 13 个 category 的检测方法、取证、误报排除、严重度、处理方式 |
| `skills/project-review/references/report-template.md` | 报告模板：章节必须与扫描器同名同序，可直接复制 |

## 0. 定位与边界

| 做 | 不做 |
|---|---|
| 在「不改行为」前提下找冗余、重复、结构漂移、文档漂移 | 不替代 `project-guide` 的日常落位（新功能该放哪，用那个技能） |
| 产出可判定、带证据的分级报告，交用户拍板 | 不替用户默认选路径、不跳过确认直接改码 |
| 按 `docs/changes/` 提案分批重构并验证 | 不自动修复、不跑 CI、不做「顺手优化」 |
| 把结论落进 roadmap / 提案 / 文档 | 不新建 `docs/` 子目录、不把临时报告留在仓库 |

### 0.1 「不改功能」的硬边界

重构批次**不得改变**下列任何一项；改动它们属于功能变更，必须另立需求（规则 12）：

| 不可变项 | 典型例子 | 怎么证明没变 |
|---|---|---|
| 命令 id 与注册项 | `open-dsh-view`（注册后完整 id 为 `dsh-native-chat:open-dsh-view`；源码里写的是短 id） | `grep -rn "addCommand" src/main.ts` 前后一致 |
| Notice 文案 | 重启成功 / 失败提示 | 文案字符串 diff 为空 |
| 状态条文案 | `DSH: 运行中` 等状态词 | `src/main.ts` 的 `'DSH: '` 前缀与 `src/service/manager.ts` 的 `onStatus('…')` 文案未改 |
| 时序参数 | 防抖 80ms、缓存 15s、SIGTERM 后轮询 3s | 数值常量 diff 为空 |
| 默认值 | 端口 3081 / profile `obsidian` / `autoStart` | `src/settings/schema.ts` 的 `DEFAULT_SETTINGS` 未改 |
| 桥契约 | `packages/dsh-obsidian-bridge` 的 v8 方法 / 页面全局对象名 | `lib/client.js` 的方法名与 payload 形状未改 |
| CSS 类名语义 | `.dsh-native-*` 的用途与层级 | `styles.css` 选择器定义与引用数不变 |
| 用户可见交互 | 键盘路由、菜单层级、焦点行为、文案 | 手动回归清单逐条过 |

判定「是不是纯搬运」只问三个问题，任一为「是」就不是纯搬运：**用户能看到的文案 / 行为变了吗？命令 id、时序、默认值变了吗？桥契约或类名语义变了吗？**

### 0.2 一次只做一类

- 同一批次里**只允许一种性质**的改动：删死码 / 纯搬运 / 收敛重复，三者不混。
- 纯搬运与改逻辑**必须分开批次**：先搬（行为完全不变）→ 构建 + 回归 → 再改逻辑；否则出问题无法判断是「搬错了」还是「改错了」。
- 一次审阅可以报很多项，但落地按第 5 节的批次顺序推进，每批结束都能单独回滚。

## 1. 六阶段流程（总览）

| 阶段 | 做什么 | 产出 | 停下等什么 |
|---|---|---|---|
| 0 冷启动 | 按 `project-guide` 读 roadmap / changes / 改动地图；**不通读源码** | 当前版本、待办、已批准提案、已知设计债 | — |
| 1 机械扫描 | 跑 `audit.mjs`，拿候选 findings | Markdown 报告或 JSON | — |
| 2 人工复核 | 逐条取证、去误报、定严重度 | 可下结论的清单（含 file:line 与证据） | — |
| 3 出报告 | 对话里给摘要 + 建议批次 + 待拍板项；完整报告存 `docs/changes/NNNN-<slug>-audit.md` | 报告 + 拍板选项 | **用户确认前不改码** |
| 4 记账 | 只报告可免提案；确认重构则登记 `R-<n>` + 提案（≥ 2 路径） | roadmap 行 + `status: draft` 提案 | **用户选路后才 approved** |
| 5 分批重构 | 文档同步 → 死码清理 → 纯搬运拆分 → 收敛重复 | 一批一提交，每批 build + check | 每批绿了再下一批 |
| 6 收尾 | 提案实施记录、roadmap 状态、文档同步、build / check / lint、手动回归 | `done` 提案 + 同步后的文档 | — |

## 2. 阶段 0~2 细节（冷启动 / 机械扫描 / 人工复核）

### 2.1 阶段 0：冷启动（5 分钟，先看文档不碰源码）

按顺序读，不要先翻 `src/`：

1. `docs/roadmap.md`：前 60 行 + 「需求待办」+ 已知设计债；
2. `docs/changes/README.md`：有没有 `approved` 未完成 / 最近 `done` 的提案；
3. `docs/development.md` 的「代码结构与改动地图」：审阅目标在哪个文件；
4. `docs/architecture.md` 的「src 分层」与「已知设计债」：分层规则与已承认的债。

```bash
sed -n '1,70p' docs/roadmap.md
grep -n '^| ' docs/changes/README.md
```

**时效性自检**（文档可能落后于代码，落后时以代码为准）：`docs/roadmap.md` 顶部「最后更新」早于最近源码改动（`find src -type f -name '*.ts*' -exec ls -lt {} + | head -3`）→ 文档漂移优先记一条；有 `approved` 提案却没「实施记录」→ 先确认改动是否已落地。

> 为什么不先读源码：审阅要判断「结构该是什么样」，答案在架构与规则里；先读源码容易被现状带跑，把漂移当成设计。

### 2.2 阶段 1：机械扫描（只读、零依赖、不联网）

#### 扫描器契约

```bash
node skills/project-review/scripts/audit.mjs [--root <dir>] [--json] [--out <file>] [--top <n>] [--min-block <n>]
```

| 参数 / 行为 | 含义 |
|---|---|
| 无参数 | 扫仓库根，Markdown 报告写 stdout |
| `--root <dir>` | 扫描根目录，默认按脚本位置向上找到仓库根（用于只审某个子树） |
| `--json` | 输出单个 JSON 对象（默认 Markdown），供二次筛选（适合管道给 `grep` / `node -e`） |
| `--out <file>` | 把报告写入文件；写出的格式与 stdout 相同（默认 Markdown，`--json` 时为 JSON），stdout 只打印写入路径与计数。完整报告归档用，见第 3 节 |
| `--top <n>` | Markdown 各列表上限，默认 10 |
| `--min-block <n>` | 重复代码块最少行数，默认 8（调大减噪、调小增召回） |

| 约定 | 值 |
|---|---|
| 报告章节（固定、顺序不可变） | `0. 概览` / `1. 超长文件` / `2. 无调用方导出与死文件` / `3. 重复实现` / `4. 结构漂移` / `5. 遗留标记` / `6. 文档漂移` / `7. 建议重构批次`（Markdown 里是 `## N. 标题`） |
| finding 字段 | `category` / `severity` / `confidence` / `file` / `line` / `title` / `evidence` / `suggestion` |
| `severity` 取值 | `high` / `medium` / `low` / `info` |
| `confidence` 取值 | `mechanical`（纯机械判定）/ `high` / `medium` / `low` |
| JSON 顶层 | `{ root, generatedAt, metrics: { codeFiles, codeLines, findings }, findings: [...] }` |
| 扫描范围 | 质量类（`long-file` / `unused-export` / `duplicate-block` / `magic-literal`）＝ `src/` + `packages/`；结构 / 遗留 / 文档类按各自规则（`doc-map-missing` 只比 `src/` 与 `docs/development.md`） |
| 排序 | 按 category 固定顺序，再按 `file`、`line` 升序（Markdown 与 JSON 同序） |
| 退出码 | 有 findings 也是 **0**；参数 / IO 错误 **2** |
| 只读保证 | 不写源码、不联网、零依赖；只读扫描根内的文本文件 |

`file` 一律是仓库相对路径，`line` 从 1 开始。

#### 怎么跑

```bash
# 1) 先看 Markdown 概览（人读）
node skills/project-review/scripts/audit.mjs

# 2) 需要逐条筛时用 JSON
node skills/project-review/scripts/audit.mjs --json > /tmp/audit.json

# 3) 复查阶段收窄范围（只审某个域 / 只留大问题）
node skills/project-review/scripts/audit.mjs --root src/view --top 20
node skills/project-review/scripts/audit.mjs --min-block 12
```

#### 怎么读输出

1. 先读 **0 概览**：文件数、行数、findings 数、各 category 命中数——决定这次审阅的重点是不是用户说的那个问题。
2. 按 **1 → 6** 章节顺序读，与第 2.3 节的复核顺序一致（死码 → 超长 → 重复 → 分层/结构 → 文档）。
3. 每条 finding 只看三样：`file:line`、`evidence`、`suggestion`；**不要直接采信 severity 与 confidence**，那是启发式初判。
4. **7 建议重构批次**只是脚本按 category 给的草案，不能当执行计划；批次由第 5 节的固定顺序 + 人工复核结论决定。
5. 脚本结果**必须人工复核**：它是候选清单，不是结论。

> **扫描范围按 category 分档**（报告 0 概览的「质量类扫描范围」行会标出）：质量类（超长文件 / 无调用方导出 /
> 重复代码块 / 重复字面量）只扫 `src/` + `packages/`，不再命中 `skills/`、`scripts/` 与扫描器自身；
> 结构类、遗留标记、文档类仍按各自规则扫全仓。`--root <dir>` 指向子目录时，质量类退化为扫该根下全部代码。

#### 两条铁律

- **脚本没扫到 ≠ 没问题**：启发式只覆盖能机械识别的模式（行数、引用计数、重复块、路径存在性）；语义重复、职责混装、文档说法错误、跨仓库契约漂移都要靠人读。
- **脚本命中的 ≠ 是问题**：组合根、状态编排器、桥单文件、真实的重复文案、生成物都可能正常命中。复核阶段逐条排除，排除理由写进报告（见 `references/checks.md` 的「常见误报」）。

### 2.3 阶段 2：人工复核（把候选变成结论）

#### 固定复核顺序

| 顺序 | 复核什么 | 为什么先做 | 主要动作 |
|---|---|---|---|
| 1 | 死码（无调用方导出 / 死文件） | 结论最硬、改动最小，先净化清单 | 全仓 grep 引用；确认桥 / 外部脚本 / 文档是否在用 |
| 2 | 超长文件 | 决定要不要拆，影响后续搬运批次 | 对照 `project-guide` 拆分判据；看是否混了两个职责 |
| 3 | 重复实现 | 最容易被误报，需要读实现语义 | 比较两处逻辑是否真的等价；能不能收敛到 `src/shared/` |
| 4 | 分层 / 结构漂移 | 涉及搬文件与 import 面，代价最大 | 对照 `AGENTS.md` 规则 11 与 `docs/architecture.md`「src 分层」 |
| 5 | 文档漂移 | 结论依赖代码，最后核对 | 以代码为准改文档；确认 roadmap 时间戳 |

#### 取证方法

- **全仓搜索，不只 `src/`**：`src` / `packages` / `docs` / `skills` / `scripts` / `styles.css` / `AGENTS.md` / `README.md` 都要搜；`main.js` 是构建产物，**排除**（否则永远命中）。
- **一次给三样证据**：位置（`file:line`）、可复现命令（grep / 计数 / 扫描器参数）、影响（不改会怎样）。
- **用计数证明「没有调用方」**：`grep -rn "<符号>" src packages docs skills scripts README.md AGENTS.md`，只剩声明处才算无调用方。
- **用 diff 证明「行为不变」**：纯搬运前后对导出名 / 字符串字面量 / 类名做 `grep` 计数对比。
- **读代码再下结论**：至少读定义 + 一个调用方；只看扫描器输出写出的报告一律不合格。

```bash
# 举例：确认一个导出是否还有调用方（排除构建产物与 node_modules）
grep -rn "serviceUrl" src packages docs skills scripts README.md AGENTS.md
# 举例：统计手写错误文案是否已收敛（0011 案例）
grep -rn "instanceof Error" src
```

#### 定严重度

严重度由「**影响面 × 误改风险 × 修复成本**」共同决定，不是脚本说了算：

| 严重度 | 判据 | 典型 |
|---|---|---|
| high | 会导致误改 / 已造成行为或契约不一致；或挡住后续改动 | 桥契约与文档不一致、分层反向 import、状态文案漂移 |
| medium | 增加维护成本、易诱发 bug，但当前行为正确 | 无调用方导出、同义实现两份、超长文件混职责 |
| low | 只影响可读性 / 一致性，改动收益低于 diff 成本 | 命名不一致、注释过期、同名导出 |
| info | 纯记录项，不排期 | 遗留标记、重复字面量、根目录杂项 |

置信度另记：`mechanical` = 机器可判定（行数 / 引用计数 / 路径存在）；`high` = 已读到实现并能复现证据；`medium` = 只做了静态搜索；`low` = 启发式命中待验证。**低置信度项不写进「建议立即做」，只列「待确认」。**

#### 每条结论必须选一个处理方式

| 处理 | 适用 | 不适用 |
|---|---|---|
| 删 | 确认无调用方的死码、死文件、临时产物 | 被桥 / 外部脚本 / 文档引用的导出 |
| 搬运 | 职责混装的超长文件、放错域的文件 | 搬运同时还得改逻辑的 |
| 收敛 | 真正等价的重复实现 | 只是长得像、语义不同的两段 |
| 只记录 | 收益低于风险、或需要用户决策的 | 已经确认可安全修的 |

## 3. 阶段 3：出报告并停下等确认

### 3.1 默认在对话里给什么

1. **摘要**：本次审了什么、扫了多少、结论一句话（例如「12 条候选，8 条成立，最大风险是桥契约与文档不一致」）。
2. **建议批次**：按第 5 节顺序列出「这批做什么 / 预计改哪些文件 / 风险」，通常 3~5 批。
3. **需要拍板**：把可选范围写成 A / B / C（如「A 只清死码；B 清死码 + 拆 2 个超长文件；C 全做」），标明推荐项与不做会怎样。
4. **完整报告落盘位置**。

### 3.2 完整报告存哪

- 文件名：`docs/changes/NNNN-<slug>-audit.md`，`NNNN` 取 `docs/changes/README.md` 的下一号（与未来提案同号，作为它的伴随文件；模板明确允许独立的长调研文件）。
- **不要**在 `docs/` 下新建子目录（`components`、`reviews` 之类），不要把报告放根目录或随意的临时位置。
- 只审不改时也保留该文件，并在报告开头注明「本次未立项」；若同一次审阅最终立项，提案正文链接它，两处状态一致。
- 报告章节与 finding 格式照 `skills/project-review/references/report-template.md`，**章节标题与顺序不可改**（必须与扫描器一致）。

### 3.3 报告质量红线

- 每条必须有 `file:line`、证据（grep / 计数 / 复现命令）、影响、建议处理方式（删 / 搬运 / 收敛 / 只记录）。
- **禁止**「建议优化」「可以更清晰」「结构不太合理」这类不可判定结论——要么给出可执行的下一步，要么标「待确认」并说明缺什么证据。
- 不能只贴扫描器输出：至少标注哪些是误报、为什么排除。
- 报告里的数字（文件数 / 行数 / 引用数）必须当场命令取，不能凭记忆或估算。

### 3.4 停止条件

报告交付后**到此为止**：不改代码、不建提案、不擅自开始第一批。用户明确说「按 A 做」之后再进第 4 节。

## 4. 阶段 4：记账（按 AGENTS 规则 12 / 13）

| 情形 | 要做什么 |
|---|---|
| 只出报告、不改码 | **可免提案**（等同纯文档改动）；报告文件留档，roadmap 不必登 `R-<n>`，除非用户要求跟进 |
| 用户确认要重构 | 必须走完整流水线：roadmap「需求待办」加 `R-<n>`（`待调研`）+ `docs/changes/NNNN-<slug>.md`（复制 `docs/changes/template.md`，`status: draft`），两处互相引用 |

提案要求：

- **≥ 2 条实现路径**，写清改动面 / 代价 / 风险，标明推荐；不确定项进提案第 8 节「需要你拍板」。
- **报告结论进提案 `1`（背景与问题）的证据表**：一条 finding 一行（位置 / 问题 / 证据），就是 `docs/changes/0011-redundancy-cleanup.md` 的做法。
- **报告结论进提案 `7`（验证）**：把报告里的可判定验收标准搬过来，写成「命令 + 期望输出」，而不是「应该没问题」。例如：
  删掉某导出后写「`grep -rn "<被删符号>" src` 无输出」；拆完文件后写「`wc -l src/view/native/ui/*.tsx` 无 > 300 行，例外需在提案里写明理由」。
  （历史写法参考：`docs/changes/0011-redundancy-cleanup.md` 第 7 节用的是「`grep -rn "serviceUrl\|resolveDshCommand\|diagnose(" src` 无输出」——符号当时已删，现在跑同一条命令自然无输出，**照抄没有意义**，要换成本次实际改动的符号。）
- 把路径选项直接呈现给用户，**等选路**；用户选定后才改 `status: approved` 并填日期。

> 不要把「审阅报告」当提案使用：报告是证据，提案是决策与执行合同；两者文件分离、互相链接。

## 5. 阶段 5：分批重构（不改功能）

### 5.1 固定批次顺序

| 批次 | 内容 | 允许的改动 | 每批结束 |
|---|---|---|---|
| 1 文档同步 | 先把已知漂移改掉（路径、事实、版本、目录树） | 只改文档 / 注释 | `npm run check` |
| 2 死码清理 | 删无调用方导出、死文件、临时产物 | 只删，不搬不改 | `npm run build` + `npm run check` |
| 3 纯搬运拆分 | 超长文件拆开、放错域的文件归位 | 只移动 / 改 import / 删空 barrel | 上一行 + 手动回归涉及面 |
| 4 收敛重复 | 合并等价实现到 `src/shared/` 或唯一归属 | 允许小改逻辑，必须证明行为等价 | 上一行 + 手动回归 |

顺序理由：文档先对齐，后面代码改动才有正确基准；死码先删，搬运时少搬垃圾；搬运先于收敛，避免一个 diff 里同时有「位置变了」和「行为变了」。

### 5.2 纯搬运的定义与纪律

**算纯搬运**：移动文件 / 新建文件接收内容 / 改 import 路径 / 删掉变空的 `index.ts`。

**不算纯搬运**（必须另起批次）：改名导出 / 改 props 或函数签名 / 合并两个组件 / 改 DOM 结构或 CSS 类名 / 顺手修 bug / 顺手改文案。

操作纪律：

- 一次只搬一个文件，搬完立刻 `npm run build`；不要攒到最后一起编译。
- 搬完对「导出名列表」「类名字面量」「用户可见字符串」做计数对比，数量不变才算纯搬运。
- 被删的 `index.ts` / barrel 必须确认没人再 import；本仓库本来禁止 barrel（规则 11），发现即记一条结构漂移。
- 不改 `styles.css` 里已有选择器的语义；只改引用位置不算改语义。

### 5.3 每批必做

```bash
npm run build        # tsc --noEmit + esbuild，main.js 必须同步
npm run check        # 版本 / 依赖 / manifest / 类型 / main.js 与源码一致 / 桥语法
```

- 改了 `packages/dsh-obsidian-bridge/`：重新 link 到 profile 并**重启 DSH 服务**，再手动验证桥接状态（v8）与面板收发；只跑语法检查不够。
- **一批一提交**，提交信息引用提案编号，保证每批可单独回滚；不要把多批压成一个 commit。
- 每批结束在提案「实施记录」里追加实际改动与验证结果；与提案有实质偏离 → 追加「变更记录」并退回 `draft` 重新确认。

### 5.4 禁止清单

- 禁止顺手改逻辑、改用户可见文案、改默认值、改时序参数——发现「这里其实该改」只记一条新 finding，不进本批。
- 禁止一次全仓大重构；禁止把「纯搬运」和「改逻辑」放在同一个 commit。
- 禁止用「反正构建能过」代替手动回归。
- 禁止为了让数字好看而删掉注释 / 文档里的证据。

## 7. 验收清单

**审阅报告质量**

- [ ] 每条有 `file:line`、证据、影响、建议处理方式；无「建议优化」类空话
- [ ] 明确标出误报及排除理由；低置信度项单列「待确认」
- [ ] 完整报告落在 `docs/changes/NNNN-<slug>-audit.md`，章节与扫描器同名同序
- [ ] 给出 3~5 个建议批次与需要用户拍板的选项（含推荐）
- [ ] 报告里的数字都是当场命令取到的

**每批重构**

- [ ] 本批只有一种性质（删 / 搬 / 收敛），没有夹带逻辑或文案改动
- [ ] `npm run build` 与 `npm run check` 通过，`main.js` 为最新构建
- [ ] 纯搬运：导出名、类名字面量、用户可见字符串计数不变
- [ ] 改桥插件：已 relink + 重启服务并验证桥接状态
- [ ] 一批一提交，可单独回滚；提案「实施记录」已追加

**最终交付**

- [ ] 提案 `done`、roadmap 行与时间戳同步、两处互链一致
- [ ] `docs/architecture.md` / `docs/development.md` / `AGENTS.md` 中受影响项已改
- [ ] 命令 id / Notice / 状态条文案 / 时序 / 默认值 / 桥契约 / 类名语义**均未变**（或有另行批准的需求）
- [ ] `docs/development.md`「现状与手动回归」相关项已过
- [ ] 仓库没有新增临时文件 / `docs/` 子目录

## 8. 反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 一次全仓大重构 | 出问题无法定位、无法回滚 | 按第 5 节固定顺序分 3~5 批，一批一提交 |
| 边搬边改 | 分不清是搬错还是改错 | 纯搬运单独成批，验证绿了再改逻辑 |
| 把扫描输出当结论 | 误报当真、漏报无人管 | 逐条人工复核，标注误报理由 |
| 删「看起来没用」的导出 | 桥 / 外部脚本 / 文档引用被打断 | 按 `references/checks.md` 的删除确认清单全仓 + 文档 + 桥契约搜一遍 |
| 跳过用户确认直接改码 | 违反规则 12/13，改动失去授权 | 报告后停住，等选路 |
| 只跑脚本不读代码 | 报告不可信、严重度乱标 | 至少读定义 + 一个调用方 |
| 把临时报告留在仓库 | 根目录 / `docs/` 变成草稿堆 | 报告进 `docs/changes/` 作伴随文件，草稿进 `/tmp` |
| 用「审阅」名义偷偷改行为 | 用户不知道行为变了 | 任何行为变更另立需求，不进重构批次 |
